# Design

## Context

本 change 延續 Sprint 1 的 mobile-first App shell、鳥寶本地資料與既有 `app-foundation`、`bird-profiles` 規格；完整動機與外部行為請見 `proposal.md` 與三份 delta spec。專案目前以本地 JSON／LocalStorage 為 MVP 資料來源，介面必須對齊 `DESIGN.md` 的 390px 版面、三個核心色彩、圓角卡片與至少 44px 操作區域。

## Goals / Non-Goals

**Goals:**

- 讓四個主要分頁共享同一個 App shell，且切換後能回到正確入口。
- 讓菜單流程從一個明確的 `bird_id` 開始，所有規則檢查都以該鳥寶為單一上下文。
- 將安全檢查放在候選菜單進入畫面前，避免先顯示危險結果再補警告。
- 以可追溯的規則結果支援每日營養綠燈，並把份量轉成廚房可用的單位。

**Non-Goals:**

- 本 Sprint 不做照顧紀錄、鳥聚點的完整 CRUD、社群互動或遠端同步。
- 不引入雲端資料庫、登入、推播或新的第三方服務。
- 不把營養綠燈當作獸醫診斷，也不取代專業醫療建議。

## Decisions

### Stitch 視覺對齊與分階段範圍

Stitch 專案 `Parrot Care Companion App`（`1093412691587248293`）目前顯示的六張手機畫面，已整理於專案根目錄 `DESIGN.md` 第 8 節。共用 shell 採 390px 單欄、左右 20px 邊距、固定四分頁底部導覽與安全區留白；卡片、按鈕、篩選籤和字級依該節元件規範。視覺方向採 Stitch 目前首頁、鸚鵡檔案與照顧紀錄畫面的暖調自然極簡風，以 `#F4F1EA` 背景、`#384D35` 森林綠及 `#B86A48` 陶土橘作跨頁基準。專案主題與菜單匯出稿仍含較早色票，菜單實作時須統一到上述共用色系。

首頁的鳥寶摘要、氣候卡、七日日期列和餐盤、菜單清單的展開卡，以及建立菜單的指定鳥寶／單日替換列，作為對應功能的畫面結構。Stitch 的示範鳥寶、天氣、營養數值和醫療說明不是資料來源。照顧紀錄完整列表與詳情雖有設計稿，仍遵守本 Sprint 的空狀態範圍；鳥聚點僅有隱藏舊稿，暫不定案完整頁面。

### 1. 用單一 App shell 管理四分頁

底部導覽由一個共用 shell 持有目前 tab，頁面內容只負責自己的資料與空狀態。這能避免每頁各自畫導覽造成選取狀態不一致；相較於用多份獨立頁面複製導覽，單一 shell 也較容易維持 390px 版面與返回路徑。

### 2. 以鳥寶上下文隔離菜單

菜單草稿、已產生菜單與目前菜單 ID 以 `bird_id` 分層保存；生成請求只接受從鳥寶檔案傳入的指定鳥寶。相較於只保存一份全域 active menu，分層保存能防止切換鳥寶後讀到錯誤的食性規則或舊菜單。

### 3. 先做規則化 preflight，再產生七日結果

生成流程依序檢查：鳥寶存在、必要食性資料完整、食材資料可用、候選不命中劇毒黑名單、鳥種專屬規則通過。任何一步失敗都回傳可理解的原因與下一步，不產生半成品。相較於生成後才過濾，前置檢查能避免危險菜單短暫出現在畫面或被保存。

### 4. 將食材規則拆成全域與鳥種層

劇毒黑名單是全域不可覆寫規則；鳥種食性、吸蜜限鐵與頻率限制是鳥種／食性層規則。候選建立時先套用全域黑名單，再套用目前鳥寶規則，最後才計算份量與營養燈號。這保留未來增加鳥種的空間，也避免把某鳥種的例外當成所有鳥種的通則。

### 5. 菜單資料同時保存原始量與顯示量

每個食材項目保留可計算的標準量，以及呈現用的 `unit`（小塊／片／顆）與必要的 `unit_scale_hint`（1 元硬幣比例尺）。營養檢查使用標準量，使用者看到的是生活化單位；這比只存文字份量更能避免顯示與判斷互相污染。

### 6. 綠燈是可解釋的規則結果

每日結果保存檢查狀態、通過或未通過原因與規則版本。畫面只呈現「綠燈／需留意／未通過」等狀態和白話原因，不使用醫療保證字眼；規則更新時可辨識舊菜單是否需要重新檢查。

## Risks / Trade-offs

- [Risk] 現有 seed 食材資料欄位不足以表達毒性、鐵含量或生活化單位 → Mitigation：先定義向後相容的預設值；資料不足時走 AC4 攔截，不猜測或自動放行。
- [Risk] 多隻鳥切換時可能殘留上一隻鳥的畫面狀態 → Mitigation：所有菜單查詢與保存都必須帶 `bird_id`，切換鳥寶時清除未提交的候選結果並重新執行 preflight。
- [Risk] 390px 下四個分頁文字與圖示可能擁擠 → Mitigation：沿用 `DESIGN.md` 的圖示優先、短標籤與 44px 觸控區，並以 Playwright 手機視窗驗收。
- [Risk] Stitch 單張匯出稿和目前主畫面使用不同版本色值，或帶有未實作的示範資料 → Mitigation：以 `DESIGN.md` 第 3、8 節的目前主畫面色系統一跨頁樣式，只使用真實資料或空狀態，截圖時核對三個核心色彩。
- [Risk] 營養規則容易被誤解為醫療建議 → Mitigation：在菜單總覽固定放置健康免責說明，綠燈只描述資料規則檢查結果。
- [Risk] LocalStorage 舊資料沒有新欄位 → Mitigation：讀取時補上空的索引結構，不刪除既有鳥寶；遇到無法判斷的資料直接顯示需補資料狀態。

## Migration Plan

1. 先加入不破壞既有鳥寶資料的導覽與本地資料索引，舊資料讀取失敗時回到安全空狀態。
2. 再加入食材規則、菜單生成與 `bird_id` 分層保存；既有單一菜單資料不得自動套給多隻鳥。
3. 完成手機版驗收後，若發現菜單規則或資料格式問題，回滾新增菜單索引與畫面入口即可，保留 Sprint 1 的鳥寶資料。
