# Design

## Context

本變更承接 `proposal.md` 與三份能力規格。專案目前已有 `DESIGN.md`、`PRD.md` 與可讀取的 `backend/species.json`／`backend/seeds.json`，但尚未有可操作的前端骨架。`DESIGN.md` 是唯一視覺標準，Sprint 1 以 390px mobile-first 為基準，資料不依賴登入或雲端服務。

## Goals / Non-Goals

**Goals:**

- 建立可從首頁開始、可進入鳥寶建檔、可重新整理恢復的最小應用流程。
- 把 `DESIGN.md` 的色彩、字級、圓角、卡片邊框與 44px 觸控規範集中成共用設計 token，避免頁面自行發明樣式。
- 以 `bird_id` 作為鳥寶資料的穩定識別，讓後續菜單功能可直接接續。
- 讓首頁健康卡在沒有外部 API 時仍能呈現，並保留日後替換資料來源的界線。

**Non-Goals:**

- 不在本 Sprint 建立七日菜單、營養計算、Smart Swap、採買、備餐、照顧紀錄或鳥聚點功能。
- 不加入天氣 API、定位權限、登入、雲端同步或後端資料庫。
- 不讓使用者自行輸入未驗證品種或自行覆寫系統判定的飲食群組。

## Decisions

### 1. 採用單一 App shell 與狀態驅動空狀態

首頁、建檔表單與後續入口共用同一個 App shell；根據本地資料是否有鳥寶決定顯示空狀態或鳥寶摘要。這比為每個畫面建立互不相干的頁面狀態更容易維持導覽與資料一致性，也符合後續 `Empty → Select Bird` 的擴充方向。

### 2. 將設計 token 集中管理

共用 token 固定使用 `#F8EADC` 背景、`#09251C` 主色、`#A55704` 強調色、`#FFFFFF` surface、`rgba(9, 37, 28, 0.65)` 次要文字色；主要卡片使用 16px 圓角與指定邊框，互動元件至少 44px 高。採用集中 token 而非散落在元件內的色碼，可讓 Playwright 截圖驗收直接對照 `DESIGN.md`。

### 3. 使用版本化 LocalStorage 根物件

資料根物件先保留 `schemaVersion` 與 `birds`，並預留後續菜單與照顧紀錄欄位的擴充空間。每隻鳥保存 `bird_id`、名字、品種、體重、飲食類型與系統帶入的飲食群組；讀取時只接受目前支援的版本，解析失敗則回到空狀態。選擇 LocalStorage 是因為 Sprint 1 需要零設定、可在瀏覽器直接測試；SQLite 或雲端資料庫留待日後需求出現再評估。

### 4. 品種資料由既有 JSON 提供，表單只呈現白名單

建檔表單從 `species.json` 取得六種支援品種與飲食群組，並將品種色票對應到 `DESIGN.md`。表單送出前再次驗證品種是否在白名單內，避免只依賴畫面選項造成無效資料。

### 5. 假天氣資料與提醒判斷分離

健康卡先使用本地固定資料來源，資料格式包含溫度、濕度、時間與來源標記；提醒判斷獨立成可測試的規則，至少涵蓋低溫、高溫與高濕度。日後接上 API 時只替換資料來源，不改變卡片顯示與免責文字契約。

### 6. 以表單驗證保護最小資料品質

名字去除前後空白後不得為空；體重必須是可解析且大於 0 的數字；品種與飲食類型必須來自支援選項。錯誤訊息放在欄位附近，送出失敗時保留使用者輸入，避免重填。

### 7. 首頁空狀態與建檔入口

首頁沒有鳥寶時，空狀態使用白色 16px 圓角卡片，搭配空飯碗圖示、短說明「先建立鳥寶，才能產生專屬飲食建議」與唯一主要 CTA「建立第一隻鳥寶」。CTA 使用 `#09251C`，高度至少 44px；插圖只作說明，不承擔唯一操作。需要鳥寶才能使用的菜單入口在空狀態隱藏或停用，避免使用者誤入無法完成的流程。

### 8. 建檔表單的手機動線與回饋

建檔採單欄直向流程：返回 → 表單標題／說明 → 名字 → 品種 → 體重（克）→ 飲食類型（系統帶入、不可覆寫）→ 送出。返回與送出視覺上分離，返回不使用與送出相同的主色按鈕樣式；輸入未保存內容後返回，先顯示可取消的離開確認。

體重輸入使用數字鍵盤友善設定（`inputmode="decimal"`，可搭配 `type="number"`、`step="0.1"`），欄位內明示「克」單位與範例。驗證規則為有限數字且大於 0；空值、空白、負數、零、非數字、無限值與貼上內容都必須攔截。錯誤文字使用 `#A55704` 或既有錯誤語意樣式，放在欄位下方並與欄位關聯；送出失敗時焦點移到第一個錯誤，欄位保留可修正內容並呈現清楚焦點框。所有欄位、選項、返回與送出控制項至少 44px 高，390px 寬度不得出現水平捲動。

## Risks / Trade-offs

- [Risk] 本地資料可能被使用者清除或瀏覽器限制 → 讀取失敗回到可理解的空狀態，並在後續版本再評估匯出或雲端同步。
- [Risk] 假天氣資料可能與真實所在地不一致 → 小卡標示為日常環境提示，不宣稱即時氣象；免責聲明固定顯示。
- [Risk] `species.json` 欄位與預期格式不一致 → 啟動時做必要欄位檢查，若無法取得白名單則停用送出並顯示資料載入提示，不接受自由輸入。
- [Risk] 設計 token 與現有元件樣式逐步漂移 → Sprint 1 的截圖驗收固定比對三個核心色與 390px 版面，後續新增元件必須沿用同一份 token。

## Migration Plan

1. 建立前端骨架與共用 token，確認空狀態首頁可載入。
2. 加入版本化 LocalStorage 與鳥寶建檔流程，再以重新整理測試資料恢復。
3. 加入健康卡、提醒規則與固定免責文字，最後執行手機版端到端驗收。

若 Sprint 1 尚未有正式使用者資料，回滾只需移除本變更建立的前端入口與本地資料讀取；不涉及外部資料庫 migration。
